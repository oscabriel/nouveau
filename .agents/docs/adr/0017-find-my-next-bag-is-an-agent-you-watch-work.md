# Find my next bag is an agent you watch work, not a form you submit

Decided 2026-09-20 (owner), recorded before any code. Implementation is a later session and is the largest item of the seven records written today. Amends the request path in `.agents/docs/recommendations.md` (Gate 2) and the `/next-bag` direction in the design handoff of 2026-09-20. Makes one explicit exception to the "no cards" rule in `DESIGN.md`.

## Context

Today `/next-bag` is a form: free text (500 characters), a USD cap, a minimum bag size prefilled at 200 g, a picker for up to five of the user's own logs, and a consent checkbox for sending their notes. `recommendations.request` queues `recommendationWorker.run` on a workpool. The worker selects up to 20 candidates by round-robin across US/USD-confirmed roasters crawled in the last hour, orders them lexically by request words, reads up to two product pages with Firecrawl for missing facts, then makes **one** OpenAI Responses call (`gpt-5.6-luna`, strict JSON schema, `store: false`, "You have no tools"). The model picks up to three product ids, copies one supplied passage verbatim each, labels the relation (similar, contrast, explore) and writes one comparison sentence, which a filter blanks if it mentions numbers, prices, stock or outcomes. The server rejects any quote that differs from its source, re-checks stock and price before storing and again on read, and every buying label comes from the database. The client subscribes to the run; the queued and running states are one sentence each, and a real run takes about twenty seconds with nothing on screen but that sentence. Results render as blocks of provenance: name, price and size, relation label, disclaimer, the OpenAI sentence, the quote, its source and time, unquoted page passages, the preference used, the market line, save and shop links.

The pipeline is honest and hard to demo. Testers were expected to read the twenty-second wait as broken (design handoff, tester plan), and the result page reads as evidence, not as a shortlist.

## Decision

**One text box.** The user types what they are looking for in plain language and nothing else. There are no other fields. A price cap, a bag size, an origin, a process, a mood, all come from the sentence or are absent. The consent note about what leaves the app stays as one grey sentence under the box.

**The run is an agent loop on the Convex Agent component, and the user watches it.** `@convex-dev/agent` is the runtime, the owner's call for the hackathon. The tools replace the pre-built candidate list: search the catalog (name, origin, process, roaster notes, price and size limits), read a lot's facts (the stored page facts, and a Firecrawl page read when they are thin, through the existing budget), check a lot's current price and stock, and read the user's own logs when the user has allowed it. Each tool is a `createTool` wrapper whose handler runs the internal queries the worker already owns, so authorization and the re-checks are the same code path as today. The twenty seconds become visible work.

**The loop's plumbing, decided in the shape conversation:**

- **The workpool still drives the run.** The component runs inside any action, so `recommendationWorker.run` stays the workpool entry: it creates the thread, then calls `agent.streamText` with `saveStreamDeltas: true`. The quotas, watchdog, one-active-run rule and retry rule are unchanged.
- **One fresh thread per run, never reused.** No chat history and no cross-run context; each run's behaviour and cost stay comparable to today's single call. The thread is the run's HOW IT LOOKED record.
- **Steps are the thread's tool-call parts.** The component persists every tool call and result as thread messages with order and stepOrder, and streams them to the client through `useUIMessages` with `stream: true`. There is no `recommendationSteps` table; writing one would duplicate the component's storage. The run document keeps what is ours: status, the request text, the consent flag, and the validated result.
- **The handoff is a `submitPicks` tool.** The model must call it to finish; its execute runs the existing validation (ids against the catalog, stock and price re-check) and writes the result to the run document, returning an error the model must fix if validation fails. Nothing is ever parsed out of free text. The model's final prose is the summary line.
- **The model is unchanged in id, changed in API.** `gpt-5.6-luna` through the AI SDK's `openai.chat` provider. The chat API persists nothing OpenAI-side, preserving what `store: false` gave. The strict Responses schema moves to zod schemas on tool args.

**Jev enters at the edges.** After the user submits, one parallel batch of Jev judgments turns the request into typed search filters (budget, bag size, origin, process, flavour direction), each a Choice or Noul, and the search tool takes them as typed args; the model may still run extra searches beyond the typed filters. After `submitPicks`, one Jev Noul per card checks that the why sentence's claims match the facts the tools returned this run; a failed check blanks the sentence. Both steps show in the step list like any tool call. Jev does not rank candidates (the model orders; a calibrated Score ranking is the later remedy if ranking proves bad), and the model never emits UI: the cards are fixed components rendering validated fields from the typed tool call.

**The result is a ranked list of simple cards.** Each card is one chosen lot: image, name, roaster, the price and size line in tabular figures from the database, and one or two sentences from the model saying why this lot fits what was asked. Up to five cards, fewer when the catalog has fewer that fit, ordered by the model's judgment of fit, top first. No relation labels, no disclaimer block, no passage lists. Save and the lot page link stay on the card. This is the one surface in the product where cards are allowed; the rest of `DESIGN.md` stands.

**What does not change.** The server still validates every id the model names against the catalog, checks stock and price from the database before storing and on read, never shows generated text as a catalog fact, and never sends the user's notes without consent. Quotas, the workpool, the watchdog, the one-active-run rule and the retry rule stay. The evidence cache and its hourly retry stay.

## Considered alternatives

- **Keep the single call and only redesign the results page.** Cheapest; the handoff's "three provenance layers without boxes" was this. It leaves the wait empty and the results as a study in citations. The owner wants the activity to feel like asking someone.
- **Stream the model's reasoning text instead of tool steps.** Prose that says "thinking about washed Ethiopians" is not evidence of anything. A tool step ("searched: washed, Ethiopia, under $30; 14 lots") is a fact the app produced and can show in tabular figures.
- **A chat thread.** Follow-up turns would be natural but double the surface (history, threads, per-turn quotas). One request, one run, one list; a new request starts a new run.
- **Hand-roll the tool loop over the Responses API.** About a hundred lines around the existing worker, keeping the strict-schema Responses call. Settled against it: the component's persisted threads and streamed steps are exactly the two things this feature sells, and adopting it for the hackathon is worth the API migration. Rejected later, if at all, on cost and latency re-measurement, not on principle.
- **Literal generative UI (the model emits layout).** Contradicts the design system and re-opens the staleness question; the structured handoff through `submitPicks` is the honest version of the idea.

## Consequences

- The verbatim-quote guarantee softens, then gets replaced twice over. The card's why is generated text that may cite what its tools returned this run (the digit filter goes), the Jev claim check blanks a why whose claims do not match the run's facts, and stock and price are still verified from the database before storing and again on read.
- Ranking moves to the model. Today the server orders candidates lexically and the model picks three of twenty unordered. Now the model searches, chooses and orders. The lexical score can remain inside the search tool as its result ordering. Jev scoring the candidates is the considered remedy if the model's ordering proves unreliable.
- The run document drops its per-event steps; the thread carries them. The run's `candidates` and `selections` shape changes with the tool loop and the `submitPicks` handoff.
- A tool loop makes several model calls per run instead of one. Cost, latency and the 45-second HTTP timeout need re-measuring on dev; the five-minute watchdog is likely still right. The per-user and global hourly quotas count runs, not calls, and stay.
- The Firecrawl budget (ADR-0010: one token, nine a minute on the Free plan) is shared with the crawler and the sweep. A tool that reads pages on demand can defer; the worker cannot wait for a slot, so a deferred read returns "no page facts" to the model and the hourly retry covers the lot, as ADR-0010 set.
- The form's history picker goes. Reading the user's logs becomes a tool the user enables with one toggle (default off) so consent stays explicit.
- Jev request-structuring adds one Typesafe call per run before the loop, and the why check adds one per card after `submitPicks`; both are small against the loop's model calls, but measure on dev.
- The thread authorization follows the run: a thread query exposed to the client must check the viewer owns the run that created the thread, the same rule as the run subscription.
- Hackathon copy: `hackathon.md`'s "What it does" line and the OpenAI entry describe the single-call design and need the new one once it ships. Judges read that file.

## Open questions

None. The runtime (the Convex Agent component on the workpool), the thread model (fresh per run, kept), the step storage (the thread, no steps table), the handoff (a validating `submitPicks` tool), the model (unchanged id, `openai.chat`), the numbers rule (allowed, verified by Jev and the server re-checks), the result count (up to five), the step display and persistence (tool line always, kept under HOW IT LOOKED), the Jev edges (request structuring, why verification, visible as steps) and the deadline rule (the loop ships only if it works on dev by Monday morning; otherwise the one-box page and cards ship on the current single-call pipeline) are all settled by the owner, 2026-09-20.

## Amendments

**2026-09-20 (implementation, batch 6). The model talks to `/v1/responses`, not `/v1/chat/completions`, and keeps `store: false` as a provider option.** The original decision moved the model id to the chat-completions provider on the reasoning that the chat API persists nothing OpenAI-side, preserving what `store: false` gave. The first live signed-in run on dev failed with a 400 before any step streamed: OpenAI rejects function tools with reasoning for gpt-5.6-luna over the chat-completions endpoint, naming `/v1/responses` or `reasoning_effort: "none"` as the supported paths. Turning reasoning off was not an option (the loop's tool work is the reasoning this model was chosen for), so the loop builds its model with the AI SDK's `openai.responses` provider — the endpoint the single-call pipeline used — and pins the effort that pipeline pinned (`low`) on the stream call. Two things ride in that option bag because the agent component's `callSettings` merge silently drops provider options: the effort, and `store: false`, because the Responses provider defaults to `store: true`, which would have let the run's messages persist OpenAI-side. The consent-on run sends the user's logs to the model; they must not outlive the run on OpenAI's side either.

**2026-09-20 (owner). Jev leaves the next-bag loop; the run is OpenAI only.** The owner's reason is the hackathon sponsor story: Find my next bag is the OpenAI showcase and should not depend on a second model vendor. Nothing was wrong with either Jev step; the recall miss logged in batch 6 ("dark roast blend" read as chocolatey, zero candidates every search) was the term filter's, not Jev's. What changes: the "Jev enters at the edges" paragraph and the two Jev items in the settled list no longer hold. The worker no longer structures the request or runs a seed search before the loop; the model's first `searchCatalog` call is the first step, and the prompt is the request text alone. The tool's typed arguments (budget, bag size, origin, process, flavour bucket) are unchanged, so the model fills them from the request itself. After `submitPicks`, no claim check runs; the why sentence stands on `submitPicks`'s validation (id against the run's candidates, stock and price re-checked) and the prompt's rule that a why cites only what the tools returned this run. The "replaced twice over" consequence becomes once over. `recommendationRuns.structured` stays optional in the schema and is no longer written; older runs keep theirs, and the page no longer reads it. `jev.ts` and the crawl-side readers (ADR-0010) are untouched. The deadline rule in the settled list still binds.

**2026-09-20 (owner). The search tool has no word filters; only budget and bag size constrain.** The first OpenAI-only run sent `flavour: fruity` on a request that named no flavour, and because `flavour`, `origin` and `process` were hard filters that required a synonym in the lot text, four searches returned 2, 1, 0 and 5 lots. The owner's rule: a person can ask for anything about coffee, so no word may exclude a lot. The tool keeps `query`, `maxPriceCents`, `minGrams` and `maxGrams`; `origin`, `process` and `flavour` are gone as arguments and go into the query words, which rank and never filter. A flavour direction word in the query ("fruity", "chocolatey") expands to the synonyms roasters write, so `FLAVOUR_SYNONYMS` now feeds `preferenceTokens` instead of a filter. `maxGrams` moved into the variant constraints beside `minGrams` and the price cap, so a lot with a large cheapest bag and a small one in range is found through the small one. The step line "Search: fruity, Guatemala, 5 lots" therefore reads as ranking words and a count, never as a filter. `structuredFilters` stays in `recommendationRules.ts` only so older runs' `structured` field validates.
